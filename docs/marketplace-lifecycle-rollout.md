# Marketplace lifecycle rollout contract
This branch prepares source code and isolated database tests. It does not migrate production, send mail/SMS, issue real invoices, refund money, or connect the courier platform.
## Default-off behavior
Leave `MARKETPLACE_LIFECYCLE_V1`, `MARKETPLACE_RESERVATIONS_ACCEPTING`, `MARKETPLACE_EMAIL_OUTBOX`, and `MARKETPLACE_LOGISTICS_HANDOFF` unset for the existing application path. New RPCs are service-only and new tables have RLS enabled with no anonymous/authenticated privileges.
Once a database contains reserved orders, keep the lifecycle processing flag enabled until those orders have settled/expired. To pause intake, disable **only** `MARKETPLACE_RESERVATIONS_ACCEPTING`; checkout then returns `CHECKOUT_PAUSED`, without falling back to unreserved writes. Keep callback/expiration processing available. Do not blindly revert the app or drop the new tables while holds exist.
## Ordered preparation
1. Capture an actual schema/constraint/function/role inventory and a restorable backup. The repository's old migrations and README are not proof of the live schema. Compare especially listing variants, seller tax/delivery fields, order status types, invoice constraints, and existing triggers.
2. Rehearse `202611120001` through `202611120009` in order on a disposable database. Never replay earlier historical/operator migrations merely to make the new functions compile. These new scripts contain no historical backfill. Migration version/column collisions are blockers, not permission to overwrite existing production data.
3. Run `npm ci --ignore-scripts`, `npm run test:isolated --workspace=@izipizi/tirgus`, `npm run typecheck`, and a build with nonfunctional test settings. SQL tests execute real embedded PostgreSQL transactions, not the actual Supabase schema. They do **not** prove multi-session concurrency or hosted Auth/RLS behavior; run two-session last-unit/expiry-vs-payment/cancellation-vs-invoice tests on the disposable full schema.
4. Inventory legacy unpaid and paid orders, incomplete tax/operator facts, existing invoices and cancelled/refunded orders. Reconcile using original evidence; do not default missing VAT to 21%, infer provider payment from `paid_at`, change historical totals, or mark an acknowledged issue as repaired. Existing invoices affected by cancellation need accountant-reviewed credit/manual adjustment.
5. Test signed Paysera callbacks in a provider-approved test project: exact, duplicate, conflicting, expired and cancelled receipts, amount/currency mismatch and retry. Browser success is read-only. `marketplace_record_refund_v1` records an **operator-attested, already executed** external refund; it neither initiates a transfer nor independently verifies a bank statement. Automatic refunds remain unimplemented.
6. Configure and verify the outbox worker separately. `MARKETPLACE_EMAIL_OUTBOX=enabled` allows sending only when the lifecycle flag and provider settings are present. Each recipient has its own durable job and stable Resend key. `accepted` means the provider accepted the request, not inbox delivery. Resend keys expire after 24 hours; uncertain sends/expired leases stay in review and must not be automatically replayed. Push, SMS, invoice-notification durability and provider delivery/bounce webhooks are not covered by this new email worker.
7. The new `/api/cron/marketplace-lifecycle` route requires `CRON_SECRET`, but is deliberately **not added to the production cron schedule** in this branch. Configure and test scheduling/monitoring only after review. Each call expires one order and processes at most one email, so size the schedule/worker throughput and alert on queue age before activation.
8. Deploy and verify an authenticated, idempotent logistics receiver before enabling transfers. This branch provides a transport interface and persisted handoff evidence, **not an HTTP receiver integration**. The generic envelope declares `marketplace-order-v1` and the stable full source key. Seller pickup snapshots are deliberately empty until explicitly verified. Receiver acknowledgement is not a courier job, physical PIN or POD. A timeout needs receiver reconciliation before retry.
9. New reserved checkout intentionally rejects nonzero promo codes (`PROMO_LIFECYCLE_REQUIRES_REVIEW`): the existing best-effort redemption/credit mutation is not an atomic promo-reservation policy. Implement and test approved concurrent promo limits/credits/funding before enabling this feature for promotional orders. Existing default-off checkout remains unchanged.
10. Obtain operator approval for a small pilot, verified access roles, notification content, settlement/accounting rules, monitoring and rollback. Only then enable lifecycle processing, followed by reservation intake and the individually verified provider integrations.
## Operational boundaries
Admin status clicks cannot manufacture a reserved payment or erase receipt evidence. Paid cancellations preserve consumed inventory pending a real return/restock decision. Shipment/delivery transitions need a recorded receiver handoff and explicit operator evidence; that evidence is an attestation, not cryptographic carrier proof. Seller acceptance uses the authenticated server endpoint; direct browser changes to reserved orders are denied.
The financial generator uses captured VAT, pickup and operator data for the new lifecycle and an atomic invoice-header/line RPC. A seller period with ambiguous legacy evidence is held rather than partially invoiced. Delivery/order discounts remain order-level and need an approved allocation before seller accounting is claimed complete. Invoice rendering and all deployed historical policies must be checked against captured operator identity before production activation.
`GET /api/admin/marketplace-readiness` is authenticated and read-only; it exposes counts rather than contacts and always reports `productionReady: false`. A green isolated build or empty review queue is not permission to migrate or activate production. This endpoint intentionally cannot certify external providers, a real receiving deployment, or human-approved rollout.
## Rollback
Pause reservation intake first; retain callbacks, expiry and durable records. Drain or explicitly reconcile every hold, unknown provider outcome and handoff. Reverting source alone is unsafe once new-order rows exist. Do not drop columns, delete reservation evidence, reset payment flags, reprice orders, or automatically restock consumed items. Restore only through an operator-approved, rehearsed recovery procedure.
